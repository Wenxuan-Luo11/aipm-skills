# 事件契约与证据审计

先问产品要判断什么，再选最少事件。不沿用其他项目的固定四个事件或漏斗。记录事件发生的业务事实、触发点、主体/会话/对象标识、字段白名单、重复条件和失败策略。

区分页面进入、真正开始、恢复、重复尝试、完成及重新开始；这些不能全由某个通用按钮点击代替。结算/支付等完成事实应来自合法状态转换；绘制、组件重复挂载、重试不能重复记账。每种计数明确分母、顺序和时间窗口。

先查已有分析 SDK/API，不为少量事件默认启用全量自动采集、录屏或持久身份。不上传密钥、完整调试日志或无关的敏感内容。公开写入 token 与个人管理 API key 分开；配置和权限按项目实际需求核实。

## 验证层级

1. 局部检查：正常路径事件顺序、恢复不重发、完成去重、重开身份、字段范围及发送失败不破坏产品。
2. 运行检查：实际浏览器/客户端操作并看记录，不只相信 mock 发送器。
3. 线上检查：配置正确项目/地区，从分析后台核对事件、字段、时间和去重；HTTP 接收也不一定等于后台已入库。

将开发与固定用例从入口隔离。运行中才启用 debug 不能撤回此前已经发送的数据；如无法做到完整排除，明确说明边界并为验收人员提供从进入就标记测试的方式。

## 分析与停止条件

没有真实数据时，只交付埋点契约、配置状态、验证结果与采集计划。少量数据标明样本数与观察范围；多次完成事件不能直接除以页面次数当人数转化。没有离开事件/心跳，不能精确声称用户何时退出；没有实验，不把相关性写成因果或改版收益。

真实反馈不足不阻塞工程过程总结；用户反馈分析能力标为待验证，不发明用户数据证明 Skill 有效。
