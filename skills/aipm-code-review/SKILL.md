# 按风险审查代码

默认只读。先确认用户要审的提交/分支、工作区及项目约束，再采集真实 diff；不因发现问题自行修改业务代码或扩大任务。

## 最短路径

1. 用现成采集脚本确定新增、删除、重命名和改动块；对照允许范围、禁改目录及必须复用项。已提交干净也要核对实际基线。
2. 样式、文案和普通辅助脚本轻量核对；核心逻辑、并发、权限、数据迁移、对外契约与发布升级，使用获授权的独立只读上下文深审。没有独立执行能力就说明限制。
3. 局部读取改动及调用者，按下列维度核实；不凭文件长度、个人风格或模型自信报问题。

## 五个维度

- **交付与测试**：实际用户路径、正式产物、有效断言及测试隔离；测试绿不等于体验完整。
- **复用与职责**：是否漏用已有组件/函数，是否混杂职责或引入不必要依赖。
- **复杂度**：真实死代码、冗余分支和可用更简单方式替代的高维护实现。
- **运行错误**：空值、越界、竞态、取消、吞错、阻塞与删除后的残留引用。
- **安全与兼容**：外部输入、权限、秘密、资源路径、旧数据/接口及失败恢复。

每条发现注明优先级、精确 `file:line`、触发条件、影响和依据；只保留可行动问题。主协调者复核独立审查的阻塞项，再安排最小修复，不照抄自报结论。

## 验收与结果

核查相关快测证据，必要时亲自运行一次；输入/版本一致的已核验结果不重复空跑。全量、端到端和打包门禁留到合并/发布前，不删除或放宽测试。修复后只复审问题及关联影响。

输出 `PASS` 或 `NEEDS_CHANGES`，列阻塞项、重要改进和验证限制。反复且跨模块的缺陷才提议沉淀规则，优先项目内检查；不自动添加常驻叮嘱。合并/发布仍按用户授权。
